# はじめに：ZTNA構成のレベルアップに向けて

これまで3回にわたって記事にしてきた**「ZTNA（Zero Trust Network Access）構成」の構築・運用検証**ですが、今回はこの構成をさらに次のレベルへと進展させるための取り組みについて共有します。

今回の最終的なゴールは、 **「Oktaのアカウントを単一の信頼できる身元（IdP）として統合し、拠点やクラウドを跨ぐ複数のサイト・リソースへのアクセスをZTNAで一元制御すること」** です。

複数サイトを安全かつシームレスにZTNA配下で制御するためには、まず社内のプライマリなグループウェアである **Google Workspace（以下、GWS）** とOktaの間で強固な認証連携（SAML SSOおよびプロビジョニング）を確立する必要があります。しかし、いきなり全社ユーザーの認証をOktaに切り替えるのは業務影響のリスクが高いため、**「Okta側で作成・同期した特定のグループに所属するユーザーのみ、Okta経由のSAML SSOを強制する」という部分的な連携（カスタムSSOプロファイルの割り当て）**を段階的に試みました。

一見すると標準的な連携手順に見えますが、GWS特キュの権限仕様やカスタムSSOならではのパラメータ管理、API権限の壁に直面し、丸一日溶かすほどの深い沼にハマることになりました。

この記事では、私が直面した「絶望的な壁（躓いたポイント）」と、Google Cloud公式のアーキテクチャドキュメントに基づいて正しくSAML / プロビジョニング連携を完成させるための完全な手順を網羅して解説します。

---

# 🚨 直面した3つの壁（躓きポイント）

設定手順に入る前に、私が数時間かけて苦しんだエラーと、その根本原因（罠）を共有します。ここを把握しておくだけで、構築作業のハマりポイントを大幅に回避できるはずです。

## 壁1: GWSの「特権管理者」はSSO設定を強制バイパスする仕様
最も時間を取られたポイントです。
特定の組織部門（OU）やグループに対してSSOプロファイルを割り当て、メインアカウントでログインテストを行ったのですが、**いつまで経ってもGoogleの標準パスワード入力画面が表示され、Oktaへのリダイレクトが発生しませんでした。**

原因は、テストに使用していたメインアカウントに**GWSの「特権管理者（Super Admin）」ロールが付与されていたこと**でした。
GWSの仕様として、管理者がSSO障害等で管理コンソールに入れなくなるロックアウト事故を防ぐため、**特権管理者権限を持つユーザーは、どんなにOUやグループでSSOを適用しても強制的にSSOがバイパスされ、Google直接認証（パスワード認証）にフォールバックされる仕組み**になっています。

## 壁2: 特権管理者を剥奪できない（契約・請求権限の壁）
壁1の仕様に気づき、メインアカウントから特権管理者ロールを外そうとしました。しかし、メインアカウントはGWSの契約当初から利用しており、Googleのお支払いプロファイル（請求管理）の所有者になっていたため、簡単に特権管理者を解除できませんでした。

**【解決策】Cloud Identity Free アカウントと「Automation OU」の活用**
公式ベストプラクティスに則り、API連携や緊急管理用の無償アカウント（Cloud Identity Free）を作成します。
さらに、このアカウントが通常のSSOポリシーの影響を受けないよう、GWS上に **「Automation（自動化用）」という独立したOU（組織部門）** を作成し、そこに管理用アカウントを隔離した上で特権管理者と請求管理権限を委譲します。
これにより、メインアカウントを「一般ユーザー（ライセンスあり・特権なし）」に安全に降格させることができ、無事にSSOの適用対象として認識させることが可能になります。

## 壁3: カスタムSSO特有の `RPID` 設定の罠（公式ドキュメントの真実）
メインアカウントがOktaへリダイレクトされるようになり、Okta側でのパスワード認証も通過したのですが、Google側にリダイレクトされた直後に以下のエラー画面が表示されました。

> **「このドメインは、シングルサインオンを使用するように設定されていません。」**

原因は**GWSのカスタムSSOプロファイルで発行される `RPID`（Relaying Party ID）の指定漏れ**でした。ドメイン全体にSSOを適用する場合は不要ですが、特定のOUやグループ単位でカスタムSSOプロファイルを作成する場合、GWS側で一意の `RPID` が生成されます。

[Google Cloudの公式アーキテクチャドキュメント](https://docs.cloud.google.com/architecture/identity/okta-provisioning-and-single-sign-on?hl=ja)を確認したところ、以下のような明確な指示がありました。

1. GWSでカスタムSSOプロファイルを作成すると、エンティティIDが `https://accounts.google.com/samlrp/RPID` の形式で発行される。
2. Oktaのアプリ設定内の **[Advanced Sign-on Settings] > [RPID]** 項目に、この `RPID` の部分だけを抽出して入力する必要がある。
3. **罠:** エンティティID全体や `/` を含めてはいけない。純粋なRPIDの文字列のみを入力する。

ここを誤ると、Google側は「どのSSOプロファイルに対する認証結果なのか」を識別できず、未設定エラーとして弾いてしまいます。

# 🛠️ 構築手順の全体像（公式ベストプラクティス版）

これらの課題を解決し、ZTNA統合に向けた認証基盤を完成させるための公式ドキュメントに準拠した構築手順は以下の通りです。

1. **事前準備**: 「Automation」OUの作成、緊急用管理者の分離、および**ルーティング設定**
2. **ステップ1**: OktaとGWSのAPIプロビジョニング設定（グループ同期と属性マッピング）
3. **ステップ2**: GWS側でのカスタムSSOプロファイルの作成とRPIDの抽出
4. **ステップ3**: Okta側へのRPIDの登録
5. **ステップ4**: GWS側で同期グループにSSOプロファイルを割り当てる
6. **ステップ5**: 動作確認・テストとZTNAへの展開

# 事前準備：「Automation」OUの作成と権限の分離

特権管理者のSSOバイパス仕様を回避し、APIプロビジョニング用のアカウントを保護するための手順です。ここで**メールのルーティング設定**を忘れると、重要なアラートが一切届かなくなるため注意してください。

1. **Automation OU の作成**:
   GWS管理コンソール（`admin.google.com`）で **[ディレクトリ] > [組織部門]** を開き、「Automation」という名前のOUを新しく作成します。
2. **Cloud Identity Freeアカウントの作成**:
   **[ディレクトリ] > [ユーザー]** から、新規ユーザー（例: `admin@your-domain.com`）を作成し、先ほど作成した「Automation」OUに配置します。※有料ライセンスは付与不要です。
3. **特権管理者の付与**:
   作成した `admin` アカウントの詳細画面を開き、**[管理者権限の役割とグループ]** から「特権管理者」ロールを割り当てます。
4. **【超重要】メールのルーティング設定**:
   Cloud Identity FreeアカウントにはGmailライセンスがないため、Googleからの重大なセキュリティアラートや、Okta連携時の通知メールを受信できません。
   GWS管理コンソールの **[アプリ] > [Google Workspace] > [Gmail] > [デフォルトのルーティング]**（またはルーティング設定）を開き、`admin@your-domain.com` 宛てのメールを、普段利用しているメインアカウントやIT管理用メーリングリストへ**転送・ルーティングするルールの追加**を必ず行ってください。
5. **お支払いプロファイルの権限委譲**:
   メインアカウントで **[お支払い] > [お支払いアカウント] > [設定を管理]** を開き、「お支払い連絡先」に `admin@your-domain.com` を追加して「すべての権限（管理者）」を設定します。
6. **メインアカウントの特権管理者解除**:
   ブラウザのシークレットウィンドウを開き、`admin@your-domain.com` で管理コンソールにログインします。
   **[ディレクトリ] > [ユーザー]** からメインアカウントを選択し、「特権管理者」ロールを削除（オフ）にして保存します。

# ステップ1：OktaとGWSのAPIプロビジョニング設定

Okta側で管理しているユーザーグループをGWS側に自動同期（Push Groups）できるように連携します。この際、Okta側のアカウントには **Super Administrator** 権限が必要です。

1. Okta Admin Console にログインし、**[Applications] > [Applications]** から `Google Workspace` アプリを追加します。
2. **[Provisioning]** タブを開き、**[Integration]** > **[Edit]** をクリックして **[Enable API integration]** にチェックを入れます。
3. **[Re-authenticate with Google Workspace]** をクリックし、先ほど作成したGWSの特権管理者アカウント（`admin@your-domain.com`）でログインしてアクセス権限を承認します。
4. **[To App]**（GWSへのプロビジョニング設定）を開き、[Edit] をクリックして以下のように設定します。
   - **Create users**: Enabled
   - **Update user attributes**: Enabled
   - **Deactivate users**: Enabled
   - **Sync password**: **Disabled** (※SAMLで認証するため、パスワードの同期は不要です)
5. **属性マッピングの注意点**:
   公式ドキュメントによると、カスタムマッピングを行う場合は `userName`、`nameGivenName`、`nameFamilyName` の3つは必須でマッピングされている必要があります。
6. 設定を保存後、**[Push Groups]** タブを開き、SSO適用対象とするOkta上のグループ（例: `GWS-SSO-Users`）を追加して同期を実行し、ステータスが `Active` になることを確認します。

# ステップ2：GWS側でカスタムSSOプロファイルの作成とRPIDの抽出

特定のグループだけにSSOを適用するためのカスタムプロファイルを作成し、Oktaに設定するための `RPID` を取得します。

## 2-1. OktaからのSAML情報の抽出
1. OktaのGWSアプリ設定画面で **[Sign On]** タブを開きます。
2. **[View SAML setup instructions]** をクリックし、表示される以下の値を手元に控えます。
   - **Identity Provider Single Sign-On URL** (`https://...` で始まるURL)
   - **Identity Provider Issuer** (`http://www.okta.com/...` で始まる識別子)
   - **X.509 Certificate** (`-----BEGIN CERTIFICATE-----` を含む証明書テキスト)

## 2-2. GWSへのSAML情報登録とRPIDの抽出
1. GWS管理コンソール（`admin` アカウント）で **[セキュリティ] > [認証] > [サードパーティの IdP による SSO]** を開きます。
2. **[SAML プロファイルを追加]** をクリックします。
3. プロファイル名（例: `Okta SSO`）を入力します。
4. 各項目にOktaから取得した値を正確に入力します。

| GWSの入力項目 | コピペ元（Okta） | 注意点 |
| :--- | :--- | :--- |
| **ログイン ページの URL** | Identity Provider Single Sign-On URL | `https://` から始まる認証URL |
| **IdP エンティティ ID** | Identity Provider Issuer | Oktaに表示された文字列をそのままコピペ |
| **検証用証明書** | X.509 Certificate | 証明書ファイルをテキストとして貼り付け |

5. 「ドメイン固有のサービスの URL」項目にある **「ユーザーをサードパーティの IdP に自動的にリダイレクトする」** にチェックを入れ、保存します。
6. **【重要】RPIDの抽出**:
   保存後に表示されるSSOプロファイル詳細画面の「SP の詳細」領域に、**エンティティ ID** が以下の形式で表示されます。
   `https://accounts.google.com/samlrp/XXXXXXX`
   
   このURLの末尾にある `XXXXXXX` の部分が **RPID（一意のID）** です。この文字列のみをメモしてください。

# ステップ3：Okta側へのRPIDの登録

取得したRPIDをOktaのGWSアプリに登録します。公式ドキュメントで指定されている正しい設定箇所に入力します。

1. Okta Admin ConsoleのGWSアプリ画面で **[Sign On]** タブを開きます。
2. **[Settings] > [Edit]** をクリックします。
3. **[Advanced Sign-on Settings]** セクションを展開します。
4. **RPID** という専用の入力フィールドを見つけます。
5. 先ほどGWSで抽出したRPIDの文字列（`XXXXXXX`）をここに入力します。
   
:::message alert
**【注意】**
公式ドキュメントに「Make sure you only enter the RPID value, not the entire Entity ID. The RPID value must not contain any / character.」とある通り、`https://...` を含めた全体や、`/` などを入れてはいけません。純粋な英数字のID部分だけを入力します。
:::

6. **[Save]** をクリックして設定を保存します。

---

# ステップ4：GWS側で同期グループにSSOプロファイルを割り当てる

1. GWS管理コンソールで **[セキュリティ] > [認証] > [サードパーティの IdP による SSO]** を開きます。
2. **[SSO プロファイルの割り当てを管理]** をクリックします。
3. 左側のリストから **[グループ]** を選択し、OktaからPushされたグループ（`GWS-SSO-Users`）を検索・選択します。
4. 右側の割り当て設定で、ステップ2で作成したSSOプロファイルを選択して **[保存]** をクリックします。

:::message
**設定反映のタイムラグについて**
GWSのプロファイル割り当て設定がGoogleの認証サーバー全体に伝播するまで、**5分〜15分程度**かかる場合があります。保存直後にテストして未設定エラーが出ても焦らず、少し時間を置いてから再度試してください。
:::

---

# ステップ5：動作確認・テスト

設定が反映されたら、対象グループに所属している一般ユーザー（特権管理者ではないアカウント）でログイン検証を行います。

1. シークレットウィンドウを開きます。
2. `https://mail.google.com/a/your-domain.com`（または `https://mail.google.com`）にアクセスします。
3. テストユーザーのメールアドレスを入力します。
4. Googleのパスワード入力画面が表示されず、**自動的にOktaのログイン画面にリダイレクトされること**を確認します。
5. Oktaでの認証成功後、エラーなくGmail等のGoogle Workspace画面が表示されれば成功です！

# まとめとZTNA統合への展望

今回の構築により、Google Workspaceにおける特定グループへのアクセス制御を、公式のアーキテクチャベストプラクティスに則ってOkta側へ完全に委譲することができました。

直面した壁と解決策を振り返ると、ポイントは以下の通りです。

- **特権管理者はSSOをバイパスするため、「Automation OU」を構築してCloud Identity Freeアカウントに管理権限を分離する。**
- **Cloud Identity Freeアカウントはメールを受け取れないため、必ずメールのルーティング設定を行う。**
- **パスワード同期はオフにし、必須属性（userName等）のマッピングを正しく行う。**
- **カスタムSSOプロファイルを使う場合、GWSのエンティティIDから `RPID` のみを抽出し、Oktaの [Advanced Sign-on Settings] の専用フィールドに正しく入力する。**

ここまでの基盤が整ったことで、当初の目的である**「Oktaのアカウントを軸にしたZTNA（Zero Trust Network Access）環境の統合」**へ向けた強固な土台が完成しました。
今後は、このOktaを唯一の認証基盤（Single Source of Truth）として、社内オンプレミスのWebアプリケーションや他のSaaSへのアクセス制御を、ロケーション問わずZTNA経由で一元管理する構成へとさらにステップアップしていきます。

同じようにGoogle WorkspaceとOktaの段階的・部分的なSSO導入で「このドメインは〜設定されていません」というエラーに苦しんでいる方の参考になれば幸いです。
