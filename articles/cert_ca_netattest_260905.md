ネットワーク認証基盤（RADIUSサーバー）のリプレイス時期は、運用ミスや想定外の挙動に悩まされることが多いタイミングです。

今回は、NetAttest EPSなどの認証基盤を「新・旧」で並行稼働させている移行期間中に、**「新しいCA（認証局）で発行するはずのクライアント証明書を、誤って古いCAで新規発行してしまった」**というケースを題材に、システムとしての挙動と、クライアント端末（Windows）の正しいリカバリ手法について解説します。

## 1. 誤って新規発行した証明書の扱いはどうなる？

NetAttest EPSで既存ユーザーに対して、誤って「新規作成」で証明書を発行してしまった場合、現在端末に入っている既存の証明書はどうなるのでしょうか？

![](https://static.zenn.studio/user-upload/8cb7b3db531c-20260905.png)

結論から言うと、**すでに端末に入っている古い証明書はそのまま有効であり、認証も可能です。**

一般的なRADIUS/CAアプライアンス（NetAttest EPSなど）の仕様として、以下の挙動をとります。

* **1ユーザーに対して複数枚の発行が可能**
  会社支給のPCとスマートフォンの両方でアクセスするケースを想定し、1つのアカウントに対して複数の証明書（NetAttestの場合は最大4〜10枚程度）を同時に発行できるよう設計されています。
* **新規発行による「上書き」や「自動失効」は起きない**
  新しい証明書を発行したからといって、過去に発行した証明書が勝手に無効化されることはありません。
* **手動で失効しない限り有効**
  管理者が管理画面から明示的に「失効（Revoke）」操作を行わない限り、有効期限内の証明書はすべて「正しい証明書」として扱われます。

つまり、システム上は単に「そのユーザーに対して有効な証明書が2つ存在している状態」になっただけであり、直ちに既存端末がネットワークから切断されることはありません。

![](https://static.zenn.studio/user-upload/f4bbe35b3215-20260905.png)

## 2. 新旧環境が混在している場合の認証挙動

次に、新旧のNetAttestが両方稼働しており、無線LANのアクセスポイント（AP）やスイッチなどのオーセンティケーターに「プライマリ：新、セカンダリ：旧」のように両方が登録されている環境を考えます。

誤って「旧NetAttest」で発行した証明書を端末に入れしまった場合、認証はどうなるのでしょうか？
答えは**「認証要求（EAP-TLS）がどちらのRADIUSに飛ぶかによって結果が変わる」**です。

### パターンA：旧NetAttestに要求が飛んだ場合 ＝ 認証成功
旧NetAttestは、自分自身（旧CA）が発行した証明書を信頼しています。そのため、誤って発行した証明書であっても正当なものとして検証され、認証を通過してしまいます。旧サーバーが稼働している間は、ユーザーは普通にネットワークに繋がってしまいます。

![](https://static.zenn.studio/user-upload/93f83480ad15-20260905.png)

### パターンB：新NetAttestに要求が飛んだ場合 ＝ 認証失敗
新NetAttestは、新しいCAのルート証明書しか信頼していません。旧CAで発行された証明書が提示されると、「信頼できない証明書」としてEAP-TLS認証で弾かれます。

![](https://static.zenn.studio/user-upload/87c37ecd8401-20260905.png)

:::message alert
**【ここに潜む罠：動作が不安定になる】**
APが「新RADIUSに問い合わせて失敗（またはタイムアウト）したので、旧RADIUSにフォールバックする」という動きをした場合、**「接続にやたら時間がかかる」「繋がったり繋がらなかったりする」**という非常に厄介なトラブルを引き起こします。
:::

これを防ぐためには、**新NetAttestで正しい証明書を作り直し、端末に配布し直す**必要があります。

## 3. Windows端末への再配布の罠（importpfxは上書きされない）

新しく正しい証明書を発行し、いざクライアント（Windows）にバッチファイル等で配布しようとする際、最も陥りやすいのが**「証明書ストアの上書きの罠」**です。

多くのインフラエンジニアは、以下のようなコマンドで証明書をインポートしようと考えます。

```bat
certutil -f -p "password" -importpfx -user "new_cert.pfx"
```

しかし、Windowsの仕様上、**同名の証明書をインポートしても「上書き」されず、「追加」されます。**
つまり、Windowsの個人証明書ストアに「旧CAの証明書」と「新CAの証明書」の2枚が存在する状態になってしまいます。

### 2枚存在することによる弊害
802.1X（サプリカント）の認証時、OSはどちらの証明書をRADIUSに提示すべきか迷ってしまい、以下の問題が発生します。

1. ユーザーの画面に「認証に使用する証明書を選択してください」というポップアップが頻発する。
2. OSが旧証明書を優先的に提示してしまい、新RADIUS側で認証エラーになる。

## 4. 正しいリカバリ用配布スクリプトの実装

上記の問題を防ぐための鉄則は、**「古い証明書を明示的に削除してから、新しい証明書をインポートする」**ことです。
コマンドプロンプト（`certutil`）を使う方法と、PowerShellを使う方法の2パターンを紹介します。

### パターンA：コマンドプロンプト（certutil）を使用する場合

`-delstore`オプションを使用して古い証明書を削除します。発行元のCA名などを指定して削除を行います。

```bat
@echo off
rem ---------------------------------------------------------
rem 1. 旧CAから発行された不要な証明書を削除
rem ---------------------------------------------------------
rem ※対象がユーザー証明書の場合は My を指定
rem "Old-CA-Name" の部分は、実際の旧証明書の発行者名等に合わせます
certutil -delstore -user My "Old-CA-Name"

rem ---------------------------------------------------------
rem 2. 新しい証明書をインポート
rem ---------------------------------------------------------
certutil -f -p "your_password" -importpfx -user "new_cert.pfx"

echo 証明書の更新が完了しました。
pause
```

### パターンB：PowerShellを使用する場合（推奨）

PowerShellのほうが、発行者（Issuer）などで厳密にフィルタリングして削除できるため、関係ない証明書を誤って消してしまう事故（誤爆）を防ぎやすく、実運用ではこちらを推奨します。

```powershell
# ---------------------------------------------------------
# 1. 旧証明書の削除
# ---------------------------------------------------------
# 対象がCurrentUserの場合（コンピュータ証明書なら LocalMachine）
$certStorePath = "Cert:\CurrentUser\My"
$oldIssuerRegex = "旧NetAttestのCA名の一部など"

# 条件に合致する古い証明書を探して削除
Get-ChildItem -Path $certStorePath | Where-Object { $_.Issuer -match $oldIssuerRegex } | Remove-Item

# ---------------------------------------------------------
# 2. 新証明書のインポート
# ---------------------------------------------------------
$pfxPath = ".\new_cert.pfx"
$pfxPassword = ConvertTo-SecureString -String "your_password" -Force -AsPlainText

Import-PfxCertificate -FilePath $pfxPath -CertStoreLocation $certStorePath -Password $pfxPassword

Write-Host "証明書の入れ替えが完了しました。"
```

## 5. 最終的なリカバリ手順のまとめ

今回のトラブルからの完全なリカバリ手順は以下の通りです。

1. **新NetAttest**で、本来想定していた正しいクライアント証明書を新規発行する。
2. **旧NetAttest**の管理画面に入り、誤って発行してしまった証明書を明示的に**「失効（Revoke）」**させる。（万が一旧環境に認証要求が飛んでも確実に弾くようにするため）
3. クライアント端末に対し、前述の**「削除＆追加スクリプト」**を用いて新しい証明書を適用する。

![](https://static.zenn.studio/user-upload/f9c4649faa6d-20260905.png)

認証基盤の移行や証明書の運用では、アプライアンス側の仕様とクライアントOS側の仕様（証明書ストアの挙動）の双方を理解しておくことが重要です。同じような事象に遭遇した方の参考になれば幸いです。
